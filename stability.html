Summary

A job may overtake (skip) an earlier job when their commutativity condition φ holds. Today's scheduler does so whenever φ holds, which is unsound. The rules below restrict when it may, and every rule but any now ends with the re-check that the Rocq proof relies on. hybrid-locked, the most permissive of the sound-intended rules, costs about 5% on the DSWP benchmarks and keeps most of the speedup of the Veracity-style programs. The re-check itself costs nothing measurable wherever there is a speedup.

The Rocq development now lets a job overtake a running job, with no new proof: every fact the soundness proof needs comes from the re-check at the overtaking job's first step, not from the condition read when it overtakes. That read only decides when to stop waiting, so the rules are performance choices, and the re-check is what has to be right.

The flags

All flags apply to vcy interp --dswp. The rule decides when a waiting job may stop waiting for an earlier job whose condition holds.

--overtake any default, unsound

Today's behaviour: skip whenever φ holds, whether the other job is waiting, running or done. No re-check.

--overtake not-started

Skip only a job that has not started yet; wait for a running one. This was the Rocq rule until 2026-11-12. --overtake-waiting-only is an alias.

--overtake hybrid

As not-started, except that a condition reading only parameters and variables that no task writes may also skip a running job: nothing it reads can change while that job runs.

--overtake hybrid-locked

As hybrid, except that a condition reading written state may skip a running job until that job first writes a variable some condition reads. Each job has a guard and a dirty flag; φ is read under the guard.

The first-step re-check

Under every rule but any, a job that overtook others checks again, just before its body starts (Rocq still_ok in SC_Local):

  1. Condition. φ still holds for each overtaken job that has not finished.
  2. Unordered. The jobs of the closure (the overtaken jobs, every job one of them still waits for, and every job one has overtaken, and so on) are pairwise unordered: no dependence relates them, or the condition of every dependence between them holds.
  3. Unspawned jobs. No job of the closure still waits for all jobs of a task that may spawn more.

It reads the conditions under the synthesized locks of the variables they read. If it fails, the job waits for the jobs it overtook, which then precede it as they would have had it never overtaken them.

Cost of the re-check

Comparing hybrid-locked with and without --no-recheck: geomean 1.05× vs. 1.00× of any on the DSWP benchmarks, 1.02× vs. 1.02× on the Veracity programs. The remaining cost is in erc20 and banking, which run slower than sequential under every rule; there the closure check fails on some re-checks.

Re-checks failed: summed over 3 runs. A first sweep with two bugs in the re-check (it required dependences in both directions, and treated a task whose jobs had not all finished as one that may still spawn jobs) gave 1.56×; both are fixed.

Can stability be checked statically?

For many conditions, yes. Each part of the re-check needs a different analysis:

  • Condition. (a) If no task writes a variable φ reads, φ cannot change: a syntactic read/write analysis the tool already does (the per-condition line of --job-stats). That covers every condition of vote, commset, commset-potrace, commset-kmeans, banking, sollve_dotprod and simple-vector. (b) Otherwise, an SMT query {φ} s_t {φ} for each task t that may write what φ reads and may run in between, with t's parameters unconstrained. This is stronger than stable3, which only covers jobs whose own conditions hold.
  • Unspawned jobs. Decided per task from the task graph: it can fail only for a task with a dependence on which its jobs wait for all jobs of the predecessor.
  • Unordered. Static when every pair of tasks whose jobs can share a closure is independent or related only by parameter-only conditions, which can then be evaluated once when the job overtakes.

Since the runtime re-check almost never fails and costs little, a static check would mostly let the paper say that most conditions are discharged statically; it would not buy much speed here.

Method

  • Tool: --overtake in src/vcy/overtake.ml; the re-check is recheck in src/vcy/interp.ml; the lock map is Lock_synthesis.task_locks. Tests: benchmarks/overtake/ in make test. Committed on branch overtake-w1.
  • The 12 benchmarks of reports/speedup_dswp.py with its inputs at N = 10⁶, and 17 programs of benchmarks/ncb/veracity/ as rewritten to pass W1 (commit dcc50b7, branch overtake-w1), in a separate Veracity-only sweep. 3 trials each, alternating sequential and the five configurations. 8 workers, --synthesize-locks, a 128-core machine.
  • Rocq: SC_DepElim in rocq/Jobs.v accepts a running job; everything rebuilds unchanged, and the main theorems use only functional extensionality.

Caveats

  • The re-check releases its locks before the body starts, matching the tool's statement-level locking. Holding the check and the whole body as one serializable unit would need whole-body two-phase locking.
  • What a waiting job still waits for is over-approximated (every unfinished job of its predecessor tasks that it would wait on). This can only add failed re-checks; it may explain some in erc20 and banking.
  • motivation seeds its array with random(), so its return value differs on every run, even sequentially. All other programs returned the same value under every configuration.
  • erc20 never resets j, so only agent 0 makes transfers (2 of them). Its numbers say little about conditions that read shared state.
  • The Veracity programs are now the repository versions: written variables dropped from the labels, and those a condition reads made global (the scheduler evaluates a condition over the labels' parameters and globals only). An earlier sweep on equivalent scratch rewrites gave 1.10× for hybrid-locked; this one gives 1.02×.
  • Whether a job overtakes depends on timing; small speedups (under about 1.3×) are within run-to-run variation. array1, conditional, counter and ht-cond-size-get kept or lost their speedup under some rule from one sweep to the next; in conditional and counter the first block writes the condition variable before its long computation.
